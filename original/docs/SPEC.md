# MES API Platform 2027 — Data Workflow · Playground 스펙

> 2026-10-20 논의 기준. 올해 구축한 서비스(Data API, 제어 API) 위에 내년(2027)에 얹을 기능을 정리한 문서입니다.
> 화면 목업은 `design` 브랜치의 `docs/mockup/`에 있습니다.
>
> 표기: **[확정]** 논의에서 정한 것 · **[가정]** 바뀔 수 있다고 한 전제 · **[예시]** 목업을 채우려고 임의로 넣은 값(실제 값 아님) · **[미정]** 아직 정하지 않은 것

---

## 1. 배경과 목표

### 1.1 이미 서비스 중인 것 (올해 구축)
- **Data API** (구 DAC): MES API Platform 사이트에서 사용자가 SQL을 등록 → 테스트 → 배포 → 실행한다. 호출 경로는 `/api/dac/select/{api_id}`. [확정]
- **제어 API**: RV 데몬을 띄워 메시지를 받거나 보낸다. `api_id`를 넣어 생성하고, RV line을 골라 어떤 메시지를 받을지 정하며, Swagger를 생성해 서비스한다. 생성 → 테스트 → 배포 흐름은 Data API와 같다. [확정]
- 서비스 대상은 반도체 생산(MES) 사내 시스템이다. 외부 공개가 아니므로 인증은 사내 기준으로 단순하게 간다. [확정]

### 1.2 내년 목표
Data API 하나(SQL 하나)로는 부족하므로 **서로 다른 Data API 여러 개를 엮는 기능**을 만든다. 이를 중심으로 다음을 확장한다. [확정]

1. **Data Workflow**: Dify 형태의 노드 편집기로 Data API를 조인·필터·머지·그룹핑해 새 API/MCP로 배포
2. **OpenAPI 3.1 명세 자동 생성**
3. **MCP 생성 서비스**: 배포한 워크플로우를 MCP 툴로 노출
4. **Playground**: 툴을 직접 호출해 보는 화면(Tool)과, 툴을 골라 Agent를 만들어 대화해 보는 화면(Agent)
5. 장기: AI Agent와 연동해 스케줄 실행, 메신저로 시스템 기능과 대화

### 1.3 이번 목업 범위
- 1. **Data API 기능 확장**: Data Workflow 에디터 · 배포 · 목록
- 2. **에이전트, 도구 Playground**: Tool Playground · Agent Playground

## 2. 용어

| 용어 | 뜻 |
|---|---|
| Data API | SQL을 등록·배포한 기존 API. 화면에서는 `DAC` 노드로 표시 |
| Data Workflow | Data API 여러 개를 노드로 엮은 흐름. 화면 이름은 영어 **Data Workflow**로 쓴다 |
| 노드 | 워크플로우의 한 단계 |
| START | 워크플로우 실행에 필요한 입력 변수를 정의하는 노드 |
| Job | 오래 걸리는 워크플로우를 비동기로 돌리는 실행 단위 |
| 워크스페이스 | 사용자가 속한 작업 공간. Data API 목록이 여기에 있다 |

노드 이름은 약어를 쓰지 않고 영어로 완전하게 쓴다. **START**, **DAC**, **JOIN**, **Filter**, **Merge**, **Group By**, **DuckDB SQL**, **END**. (`JN` 같은 약어, `DB` 표기는 쓰지 않는다.) [확정]

## 3. 전체 구조 (가정)

시스템 구조도는 목업에서 뺐으나, 논의한 전제는 다음과 같다.

```
호출하는 쪽 ─ 웹(MES API Platform) / 사내 시스템(HTTP) / AI Agent·메신저(MCP)
        │
   API Gateway (인증·라우팅)
        │
 ┌──────┴──────────────────────────────┐
 │ Workflow Service  : 정의·버전·배포 상태 저장, 명세 생성 │
 │ Workflow Runner   : 노드 실행, 조인·필터·그룹핑은 DuckDB │
 │ MCP Host Server   : 배포한 워크플로우를 MCP 툴로 노출   │
 └──────┬──────────────────────────────┘
        │ 노드 실행 시 호출
   Data API(DAC) ─ Session Manager / Worker ─ Oracle 19c
   제어 API ─ RV 데몬
```

- **DuckDB는 공유 1대**를 띄워 둔 것으로 가정한다. 나중에 **인스턴스(실행 단위별)로 바꿀 수 있다.** [가정] (Plan B)
- **MCP 호스트 서버도 공유 1대**가 있는 것으로 가정한다. 나중에 **워크플로우마다 별도 서버**로 바뀔 수 있다. [가정] (Plan B)
- Plan B가 있으므로 DuckDB·MCP 호스트는 Workflow Runner / MCP Host 뒤에 숨겨서, 바뀌어도 화면과 API는 그대로이게 설계한다.
- Workflow Service가 워크플로우 정의·버전·배포 이력을 저장할 저장소가 필요하다. 어떤 DB를 쓸지는 [미정]
- 워크플로우를 직접 구현하되, 나중에 Dify를 직접 연결하는 방식으로 바꿀 수도 있다. [가정]

## 4. Data Workflow 에디터

### 4.1 기본 형태
- Dify처럼 캔버스에 노드를 놓고 선으로 잇는 **자체 구현 노드 편집기**. Dify를 직접 쓰지 않는다. [확정]
- 노드 추가는 **캔버스 빈 곳 우클릭**으로 한다. (상단 노드 추가 툴바는 두지 않는다.) [확정]
- 화면 구성: 상단 헤더(제목·상태·테스트 실행·저장·배포), 중앙 캔버스, 오른쪽 노드 설정 패널, 하단에 붙은 실행 결과 바(탭: 결과 / 입력값 / 노드별 실행, 성공 여부·노드 수·소요 시간·행 수 요약, "결과 펼치기").
- 각 노드는 종류별 색 띠 헤더(아이콘+영문 이름)와 실행 상태 점·소요 시간을 가진다.

### 4.2 노드 종류

| 노드 | 설명 | 상태 |
|---|---|---|
| START | 입력 변수 정의 | 확정 |
| DAC | 배포된 Data API 하나를 호출 | 확정 |
| JOIN | 두 입력을 키로 조인 (DuckDB) | 확정 |
| Filter | 조건으로 행 거르기 (DuckDB) | 확정 |
| Merge | 두 결과 합치기 (DuckDB) | 확정 |
| Group By | 그룹핑·집계 (DuckDB) | 확정 |
| DuckDB SQL | 직접 SQL 작성 | 확정 |
| END | 출력 컬럼 정의 | 확정 |
| Control API 노드 | 제어 API 호출 | 준비 중 |
| Sensor API 노드 | 센서 이벤트 | 준비 중 (목업 보드는 삭제) |

### 4.3 START 노드 (Dify 방식)
- 워크플로우를 실행할 때 필요한 **입력 변수를 START 노드에서 정의**한다. 변수마다 이름·타입·필수 여부를 가진다.
- 예: 노드1에서 `lot_id`, `wafer_id`가 필요하고 노드2에서 `start_time`, `end_time`이 필요하면, START에서 4개를 정의하고 실행 시 4개를 모두 받는다.
- 노드 쪽에서는 START 변수를 참조하거나 앞 노드의 출력을 참조하거나 고정값을 입력한다. (Dify의 변수 참조 방식과 같게 한다.)
- 자체적으로 만들 수 있는 값만 쓰는 워크플로우는 입력 변수가 없어도 된다.
- 이 변수 정의가 그대로 **API 요청 본문과 MCP 입력 스키마**가 된다. (배포 화면에 입력 변수 표를 따로 두지 않는다. [확정])

### 4.4 DAC 노드
- 사용자가 속한 **워크스페이스의 이미 배포된 Data API 목록**에서 고른다. (내부 시스템이므로 권한은 워크스페이스 기준으로 단순하게.) [확정]
- 선택 UI는 **펼쳐지는 콤보박스**: 상단에 현재 선택, 아래에 검색창과 API 목록(이름·설명·버전). 배포되지 않은 API는 흐리게 표시하고 선택할 수 없다. [확정]
- 오른쪽 패널에 **API 정보**를 작게 보여준다: DB 종류(Oracle 19c), DB 이름, 등록된 Oracle SQL(바인드 변수 포함). [확정]
- 파라미터 연결: API의 각 파라미터에 START 변수, 앞 노드 출력, 고정값 중 하나를 연결한다.
- 출력 컬럼 목록, 실행 옵션(타임아웃, DuckDB 적재 한도)을 설정한다. [예시: 30s, 100,000행]

### 4.5 실행 방식
- DAC 노드의 결과를 **DuckDB에 적재**해 조인·필터·머지·그룹핑을 수행한다. [확정]
- 노드 단위로 실행 상태와 소요 시간을 기록해 "노드별 실행" 탭에서 본다.

## 5. 배포

### 5.1 배포 대상
- **API와 MCP를 둘 다 선택**할 수 있다. 하나만, 둘 다, 어느 쪽도 가능. [확정]
- 두 카드를 세로로 쌓고 각각 체크로 켜고 끈다. 켠 카드 안에 해당 설정이 펼쳐진다.

### 5.2 API 배포
- **호출 경로: `POST /api/workflow/{api_id}`**. 기존 Data API 경로(`/api/dac/select/{api_id}`)와 겹치지 않게 별도 경로를 쓴다. [확정]
- 배포 시 **OpenAPI 3.1 명세를 자동 생성**하고 Swagger UI를 제공한다(사내망 공개). [확정]
- 설정 항목: api_id, 워크스페이스, 인증(사내 토큰), Swagger UI 공개, 타임아웃, 호출 제한. [항목은 제안, 값은 예시: 30s, 60회/분]
- 호출 라우팅은 우리 쪽 자체 라우팅 방식을 쓴다(별도 게이트웨이 제품 없음). [확정]

### 5.3 MCP 배포
- 워크플로우가 **MCP 툴 하나**로 노출된다. 전송 방식은 streamable-http. [확정]
- 설정 항목: MCP 서버, 툴 이름, **툴 설명**(LLM이 읽고 호출 여부를 판단), 접근 권한. [항목은 제안]
- 툴 입력 스키마는 START 변수에서 자동 생성한다.

### 5.4 실행 방식: 동기 / Job (비동기)
Data API 여러 개를 엮으면 오래 걸릴 수 있으므로, 실시간 응답이 아닌 방식을 선택할 수 있다. [확정]

| | 바로 실행(동기) | Job으로 실행(비동기) |
|---|---|---|
| 동작 | 끝날 때까지 기다려 결과를 바로 응답 | job_id를 즉시 반환하고 뒤에서 실행 |
| API 응답 | `200` + 결과 | `202 Accepted` + `job_id` |
| 결과 확인 | 응답에 포함 | `GET /api/workflow/jobs/{job_id}` 로 조회, 또는 **완료 웹훅** |
| MCP | 툴 1개 | 워크플로우 툴(job_id 반환) + `get_job_result` 툴(상태·결과 조회) |

- 웹훅은 완료·실패 시 POST로 알린다. 비워 두면 조회로만 확인한다.
- 재시도 횟수와 결과 보관 기간은 정해야 한다. [미정, 목업 예시: 실패 시 3회 재시도, 결과 7일 보관]
- Job 큐·워커가 필요하다. 구현 방식은 [미정] (올해 구성에 RabbitMQ가 있으므로 활용 여부를 검토)
- 배포 화면의 오른쪽에는 **OpenAPI 3.1 / MCP 툴 스키마 미리보기**를 탭으로 보여주고, 실행 방식에 따라 미리보기도 바뀐다.
- "배포 전 확인" 체크리스트(테스트 실행 성공, 필수 변수 정의, 사용한 Data API 모두 배포 상태)를 통과해야 배포할 수 있다.

## 6. Data Workflow 목록

- MES API Platform의 **한 메뉴**로 들어간다. 따라서 플랫폼 공통 레이아웃을 따른다. [확정]
  - **맨 위 탑바**(로고 A, 서비스 이름, 워크스페이스, 사용자)
  - 그 아래 **왼쪽 아이콘 전용 사이드바**(글씨 없음, 줄인 상태): 홈 · Data API · 제어 API · Data Workflow · Tool Playground · Agent Playground
- 상단 요약 카드: 전체 / 배포됨 / 24시간 호출 / 확인 필요.
- 탭: 전체 · 배포됨 · 초안 · 확인 필요. 검색: 이름·경로·툴 이름.
- 표 열: **워크플로우(영문 ID)**, 상태, 배포 대상(API / MCP / Job 칩), 호출 주소·툴, 버전, 24시간 호출 수, **배포자**, 수정 시각.
  - 워크플로우 제목은 한글이 아니라 **영어 ID 형식**(`lot_yield_equip`)으로 표시한다. 호출할 때 쓰는 값이기 때문. 설명(description)은 한글 그대로. [확정]
  - 제목 앞에 작은 워크플로우 아이콘(옅은 노란색)을 둔다.
- **페이징은 표 맨 아래에 고정**한다. [확정]
- 상태: 초안 · 배포됨 · 확인 필요(연결된 Data API가 배포 취소되는 경우 등).

## 7. Playground (두 화면으로 분리)

처음에는 MCP·Agent 확인용 화면 하나였으나, 성격이 달라 두 화면으로 나눴다. 대상 사용자는 **API 개발자**. [확정]

### 7.1 Tool Playground
Agent(LLM)를 거치지 않고 **툴 하나를 직접 호출**해 결과를 확인한다. 툴이 문제인지 프롬프트가 문제인지 가려내는 용도.

- 왼쪽: 툴 목록(서버별 묶음 — MCP 서버, Data API, 제어 API(준비 중)), 검색, Job 툴은 "Job" 칩.
- 가운데: 선택한 툴 이름·설명, 입력 스키마에서 만든 입력칸(타입·필수), 호출 버튼.
- 오른쪽: 응답/요청 탭, 상태·소요 시간·행 수, 응답 JSON, 최근 호출 기록.

### 7.2 Agent Playground
간단한 **에이전트 빌드와 대화**를 한 화면에서 한다. 3컬럼. [확정]

1. **내 Agent**: 만든 Agent 목록(여러 개), "+ 새 Agent", 상태(초안/저장됨), 저장된 Agent는 "사용" 버튼으로 바로 대화.
2. **설정**: 에이전트명, 모델, **프롬프트**, **사용할 도구**(우리가 만든 MCP·워크플로우·Data API 툴을 체크박스로 선택), 스케줄, 메신저 연결(준비 중).
3. **Agent 채팅**: 질문 입력, 어떤 툴을 어떤 값으로 호출했는지 호출 기록 표시, 응답.

용어: "이름"은 **에이전트명**, "지시문"은 **프롬프트**로 쓴다. [확정]

## 8. 후속 · 보류

- **제어 API**: 2027년에 **Kafka 메시지 지원 확대** 예정. 제어 API를 워크플로우 노드·Playground 툴로 쓰는 것은 "준비 중". [확정]
- **Sensor API**: 이벤트나 특정 조건 충족 시 알람. 추가 예정이나 목업은 복잡하기만 해서 뺐다. 이후 Event Bridge(센서 연결)와 함께 재논의. [미정]
- **LLM Gateway**(멀티 모델 선택 라우팅): 목표에는 있었으나 목업 화면은 삭제했다. 범위는 [미정]. 현재 Agent는 모델을 직접 선택하는 단순 구조.
- **스케줄 · 메신저 연동**: Agent 설정에 항목만 두었다(꺼짐 / 준비 중). 세부 설계는 [미정].
- **시스템 구조도**: 목업 보드는 삭제했다. Job 큐·워커를 반영해 다시 그린다. [미정]

## 9. 화면 규칙

- 한국어 화면, 노드·메뉴·모드 이름은 영어 사용.
- 로고: 검정에 가까운 네이비 배경 + 채도 낮은 파란색 **"A"**. (체크박스와 헷갈리는 파란 그라데이션 "M"은 쓰지 않는다.) [확정]
- 색: 포인트 인디고(#4f46e5 계열), 배경 #f6f7f9, 카드 흰색, 노드 종류별 색(START 인디고 / DAC 파랑 / 변환 노랑 / END 회색).
- 글꼴: Geist · IBM Plex Sans KR · Geist Mono. 기본 14px, 카드 둥근 모서리 14px.
- 보드(화면) 크기: 1440×960 통일.
- 참고 디자인: 기존에 만든 SQL 추천 에이전트 채팅 UI.
